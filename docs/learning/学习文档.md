# EvalFrog 学习文档

本文档用于项目完成过程中的持续复盘，以及一周后的面试集中复习。内容只记录已冻结的设计或已实现并验证的能力；尚未完成的部分会明确标为“待实现”。

## 1. 一分钟项目介绍

EvalFrog 是一个同时面向 Human Web Canvas 与 Agent CLI 的企业级 Workflow Platform。Human 和 Agent 都编辑 Canonical JSON IR，平台在服务端完成校验和编译，Runtime 只执行不可变 DSL Snapshot。系统用 Source Map 把 DSL 运行错误无损映射回 IR Node、Edge 和字段路径；用 Engine、Scheduler、Attempt Coordinator、Worker 的职责分离保证状态推进、项目公平调度和节点执行可以独立扩展。

第一阶段重点不是扩充节点生态，而是跑通“创建 IR → 校验 → 测试 → 发布 → 正式运行 → 错误定位”的最小闭环，并确保 PostgreSQL、Redis 和 Kafka 的职责清晰。

## 2. 当前架构心智模型

```text
Human Web / Agent CLI
        ↓ Canonical IR
Modular Control Plane
  Definition → Compiler → Immutable DSL + Source Map
  Runtime Engine ↔ Scheduler ↔ Attempt Coordinator
        ↓                 ↓
PostgreSQL            Scheduling Redis
        ↓ Outbox           ↓ bounded dispatch
      Kafka → Builtin Worker / Sandbox Worker
                    ↓
             Execution Context Gateway
                    ↓
          PostgreSQL + Cache Redis
```

核心职责：

- PostgreSQL：Definition、Runtime State、Output、Outbox/Inbox、权限和审计的唯一权威来源；
- Scheduling Redis：维护可重建的 Lane、Credit、Ready Index 和 Inflight Reservation，加速高频调度；
- Cache Redis：缓存 Snapshot、Run Context、Effective Output 和 Read Model，Cache Miss 回源 PostgreSQL；
- Kafka：承载 Task 与 Runtime Event 的至少一次传递，不保存权威业务状态；
- Worker：只执行一个已 Claim 的 Attempt，不直接推进 Workflow 状态。

## 3. 高频面试问答基线

### Q1：为什么不能直接让 Runtime 执行 IR？

IR 服务 Human 和 Agent 的编辑、理解、Diff、Copy 与布局表达，允许 Draft 不完整；DSL 服务 Runtime，需要强约束、版本化和确定性。分离后，编辑模型可以演进，历史发布版本仍由不可变 DSL 稳定执行。代价是必须维护 Compiler、兼容性规则和 Source Map。

### Q2：为什么 Draft 测试也必须执行不可变快照？

测试可以从 Draft Revision 触发，但 Run 创建时必须绑定当时编译出的不可变 Execution Snapshot。这样执行期间继续编辑 Draft 不会改变本次 Run，也能复现错误。正式运行只能绑定 Published Version；没有发布版本不能正式调用。

### Q3：数据库、Redis、Kafka 为什么要这样分工？

PostgreSQL 提供事务、约束和可恢复的权威状态；Redis 解决短期高频读取和调度索引问题，但数据可丢失并可从数据库重建；Kafka 解耦生产者与消费者、吸收流量波动并提供至少一次传递，但消息偏移不能替代 Workflow 状态机。三者是权威状态、派生加速和异步传输的分工，不是为了堆技术栈。

### Q4：为什么权威运行数据不使用 Redis Write-Behind？

Node Output 和状态迁移会决定后续节点能否运行，先写缓存再异步落库会产生丢失、乱序和成功响应后不可恢复的问题。正确路径是先在 PostgreSQL 原子提交状态、Output 与 Outbox，再删除或刷新 Cache；后续读取命中 Redis，不命中回源。缓存不在关键写入的正确性路径上。

### Q5：Kafka 已经投递任务，为什么还需要 Attempt、Lease 和 Fencing？

Kafka 是至少一次传递，重复消费、消费者崩溃和延迟消息都正常存在。Worker 必须先通过数据库 CAS Claim Attempt，获得 Lease 与 Fencing Token；只有当前有效 Attempt 的完成结果才能成为 Effective Output。Kafka ACK 表示任务已被可靠接管，不表示节点已经成功执行。

### Q6：为什么 Scheduler 不采用全局 FIFO？

一个 Project 瞬间产生大量 Task 时，全局 FIFO 会让其他 Project 长时间等待。EvalFrog 以 `project_id` 为唯一公平单元，在活跃 Project 间做等权 Max-Min Fairness，空闲额度允许借用；Project 内再按优先级和就绪时间稳定排序。固定 Scheduling Lane 将高频竞争限制在分片内，跨 Lane 只批量分配 Credit，便于 Redis 水平扩展。

### Q7：为什么 Kafka 前需要有界 Dispatch Window？

如果把大量尚未获得实际执行容量的任务提前塞入 Kafka，Broker 队列顺序会固化旧的调度决策，后续新 Project 即使应获得公平额度也只能排在深队列后。Dispatch Window 只允许有限数量的已准入 Attempt 在途，让 Scheduler 能持续重新计算公平性并提供背压。

## 5. M0：仓库骨架与架构护栏

- 验收状态：已通过本地 Unit、Race、Vet、Build、Architecture、Compose、Integration 与 Graceful Shutdown 验收，并已通过远端 CI、合并到 `main`。
- 学习价值判断：写入。
- 判断理由：M0 体现了模块化单体、Composition Root、启动时配置校验、数据库迁移、健康检查、优雅停机和自动化架构测试，是面试中解释“如何防止架构只停留在图上”的关键证据。

### 解决的问题

M0 不实现 Workflow 业务，而是先建立可执行的边界：四个程序能独立构建和启动，Control Plane 与 Worker 拥有不同依赖权限，三套环境配置遵守同一可靠性语义，本地依赖和 CI 可以重复创建与验证。

### 核心边界与不变量

- `cmd` 只有 `evalfrog`、`control-plane`、`worker-builtin`、`worker-sandbox` 四个 Composition Root；
- `cmd` 只做配置、依赖装配和生命周期管理，领域逻辑不得进入 `main`；
- Worker 只装配 Kafka 与 Worker API Client，没有 PostgreSQL Client 或凭证；
- 版本化 Profile 不保存数据库密码，Compose 只向 Control Plane 与 Migration 注入 PostgreSQL/Redis 连接变量；
- Domain 不得导入 Adapter，Runtime 不得读取 IR/Definition/Catalog，Scheduler 不得导入 Engine；
- `local/test` 继承 `production-default`，只覆盖容量和环境隔离项，可靠性边界不会因环境变小而改变；
- Profile 只在启动时选择，不支持运行期热切换。

### 最终方案及原因

采用模块化单体 Control Plane 加独立 Worker 进程，而不是立即拆微服务。代码边界先通过包结构和自动化依赖测试固定；未来部署拆分只需替换进程内 Port 的 Adapter，不重新定义状态所有权。

所有环境使用严格 YAML：先加载完整 `production-default`，再递归覆盖 `local/test`，最后应用有限的环境变量。解码拒绝未知字段，启动校验检查 Profile 隔离、Kafka 分区、Lease/Heartbeat、Reservation、Inbox Retention 和 PostgreSQL 连接预算，避免错误配置进入运行期。

容器运行层使用静态 Go 二进制和 `scratch` 镜像。每个服务二进制提供自身 HTTP Probe，因此健康检查不依赖 Shell、curl 或 wget，镜像更小且攻击面更低。

### 被放弃的方案及原因

- 大量微服务：M0 没有独立扩缩容和团队所有权证据，提前拆分只会增加网络与一致性成本；
- 全局 `common/utils/service` 包：容易让任意模块绕过所有权，形成新的大泥球；
- Worker 复用 Control Plane 数据库 Client：部署方便但破坏状态写入边界，执行层漏洞也会获得数据库权限；
- 每套环境复制完整配置：容易发生参数漂移，测试环境无法代表生产语义；
- 配置热更新：Lease、分区、Lane 和连接池参数跨实例不一致会产生难以推理的运行行为，第一阶段只允许重启生效；
- 应用启动时自动执行 Migration：多实例启动会把发布与 Schema 变更耦合，M0 使用带 Advisory Lock 和 checksum ledger 的独立 Migration 模式。

### 数据库、Redis 与 Kafka 在 M0 的角色

- PostgreSQL：只创建 Profile 隔离 Schema 与 Migration Ledger，尚无 Workflow 业务表；
- Scheduling Redis：独立 Endpoint、`noeviction`，为后续 Lane/Credit/Reservation 提供故障域；
- Cache Redis：独立 Endpoint、`allkeys-lfu`，证明读取缓存可以独立淘汰；
- Kafka：禁用自动建 Topic，由部署脚本显式创建 Builtin Task、Sandbox Task、Runtime Event 和 DLQ；M0 尚不投递业务消息。

这一步的重点是提前证明三者能够独立启动、健康检查和配置隔离，不是用它们假装已有业务吞吐能力。

### 一致性与故障恢复

Migration Runner 使用 PostgreSQL Advisory Lock 串行化多实例迁移，以版本号和 SHA-256 checksum 记录不可变历史；每个事务用 `SET LOCAL search_path` 锁定目标 Schema，避免复用连接池时把 SQL 执行到错误环境。重复执行幂等，已应用 SQL 被修改时直接失败。进程收到 SIGTERM 后按逆序关闭服务，并受统一 Shutdown Deadline 限制。实测三个长运行进程在约 3.36 秒内以退出码 0 停止并能健康重启。

### 高频面试题

#### Q：什么是 Composition Root，为什么只允许它依赖具体 Adapter？

Composition Root 是创建对象、选择实现并连接依赖的唯一位置。领域模块只依赖 Port，具体 PostgreSQL、Redis、Kafka 实现在最外层注入，业务代码因此可以独立测试，也能在不改变领域模型时替换传输或存储实现。

#### Q：模块化单体和普通单体有什么区别？

区别不在进程数量，而在依赖方向、数据所有权和稳定接口。EvalFrog 第一阶段同一 Control Plane 进程内包含多个模块，但禁止反向 Import 和绕过 Owner 写状态；未来拆服务是部署变化，不是重新发明领域边界。

#### Q：Liveness 与 Readiness 有什么区别？

Liveness 只回答进程是否活着，不应因为下游短暂故障而触发无限重启；Readiness 检查当前实例能否接流量。Control Plane Readiness 检查 PostgreSQL、双 Redis 和 Kafka，Worker Readiness 只检查 Kafka 与 Control Plane，不检查它无权访问的数据库。

#### Q：为什么迁移需要 Advisory Lock 和 checksum？

Advisory Lock 防止多个发布实例并发应用同一批迁移；checksum 防止已经在某环境执行过的 SQL 被原地修改。前者解决并发，后者保护历史不可变性，两者不能互相替代。

#### Q：为什么配置错误必须启动失败？

Heartbeat、Lease、Kafka Partition、Redis Reservation 和数据库连接池之间存在硬约束。若实例带着不一致配置运行，问题只会在故障或高并发时出现，恢复成本远高于部署时 Fail Fast。

### 一分钟讲法

M0 的核心不是“建目录”，而是把架构图转成可执行约束。我建立了四个 Composition Root，Control Plane 可以访问 PostgreSQL、双 Redis 和 Kafka，Worker 只能访问 Kafka 与 Worker API；自动化架构测试会拒绝反向依赖。三套配置通过继承保持相同可靠性语义，并在启动时校验容量关系。本地 Compose 显式创建基础设施和 Kafka Topic，Migration Runner 用 Advisory Lock 与 checksum 保证并发和历史安全，所有进程支持健康检查、Trace、Metrics 与统一优雅停机。

## 6. M1：IR、Node Catalog Contract 与公共契约

- 验收状态：已通过 Unit、Contract、Golden Fixture、20 次重复、Bounded Fuzz、Vet、Build 与 Linux Race 验收；远端 CI 由本模块分支提交触发。
- 学习价值判断：写入。
- 判断理由：IR 是 Human Web 与 Agent CLI 的共同语言，Logical ID、类型系统、Catalog Version、Canonical Hash 和宽松保存/严格发布边界都是后续难以迁移的底层决策，也是编译器、DSL 和错误回溯的前置条件。

### 解决的问题

M1 把“作者可以提交什么”从聊天中的 JSON 示例变成版本化机器契约。Web 随机 ID 与 Agent 语义 ID 使用同一种 IR；节点差异由 Catalog Description 表达，不能把运行时 Operation Version、Worker 或 Kafka 细节泄漏给作者。

### 核心边界与不变量

- IR 顶层只有 `ir_version/nodes/edges/layout`，Node 统一为 `id/type/title/inputs/outputs`；
- Input 通过 `source=literal|ref` 互斥表达值或上游命名 Output，不存在 `params`、Port 或 Binding ID；
- Node/Edge Logical ID 由作者离线生成，支持 UUID 和语义 ID；Node Version 不进入 IR；
- 顶层类型只有 `string/integer/number/boolean/object/array`，顶层不允许 Null，只有 `integer → number` 隐式提升；
- Draft Parser 允许语义不完整但安全的 IR 外壳，Strict Validator 必须显式绑定 Catalog；
- Catalog 内部版本化，Web/Agent 只获得无版本号且不可修改权威状态的 Description 防御性副本；
- Canonicalize 对 Object Key 顺序不敏感、对 Array 顺序敏感，Hash 使用 SHA-256；
- Diagnostic 使用稳定 Code 和 IR Location，排序确定且最多返回 100 项。

### 最终方案及原因

Go Model 保持浅层统一外壳，`json.RawMessage` 只用于 Literal Value，使十进制 Number 不被提前转成 `float64`。Parser 在模型解码前执行文档大小、深度、Collection、String、Number、UTF-8、Unicode Surrogate 和重复 Object Key 检查；成功后再拒绝未知作者字段。

Strict Validator 先检查 ID、Input/Output、Literal、Edge、Layout 和 Ref 类型，再通过接口调用固定 Catalog Revision。`internal/ir` 不导入具体 `internal/catalog`，Catalog 反向实现 Node Contract Port，因此新增普通 Task Node 不需要修改 IR Validator 的中心分支。

Canonical JSON 使用精确十进制归一化，不经过二进制浮点；Object Key 排序、Array 保序、Number 和 String 编码规则均由 Golden Test 固定。这样 Draft Revision、Published Snapshot 和未来 Definition Hash 才能跨实例稳定复现。

### 被放弃的方案及原因

- 为每个 Node Type 定义不同 JSON 外壳：Agent 必须理解大量私有结构，新增节点会修改 IR 核心 Schema；
- 把 Node Version 放进 IR：Web/Agent 被迫参与内部兼容性选择，旧 Draft 容易静默改变语义；
- 只有 JSON Schema：Schema 无法校验 Input/Output 唯一、跨节点 Ref、Catalog 规则和稳定 Diagnostic Location；
- 只有 Go Validator：Web、CLI 和其他语言无法消费版本化机器契约；
- 服务端生成 Logical ID：离线 Agent 无法独立生成和最小化修改 Workflow；
- 直接使用 `map[string]any` 和 `float64`：字段边界不清晰，大整数和 Decimal 会发生精度损失；
- Draft Save 直接执行完整校验：Web 自动保存会因临时断边或半成品节点失败；
- 接受重复 JSON Key 或非法 Surrogate：不同解析器可能得到不同语义，Canonical Hash 失去可信度。

### 数据库、Redis 与 Kafka 在 M1 的角色

M1 是纯 Contract/Domain 模块，不读写 PostgreSQL、Redis 或 Kafka。IR Hash 将来由 Definition 持久化，但 M1 不为了展示技术栈而给确定性解析和校验引入基础设施依赖。

### 一致性、安全与容量

确定性来自三层证据：版本化 Schema/Fixture、Canonical Golden、同一 Fixture 重复 100 次得到相同字节和 Hash。安全边界包括 1 MiB 文档、64 层深度、256 KiB String、10,000 Collection、128 Port 和 100 Diagnostic 上限，防止 Agent 生成的异常 JSON 消耗无界 CPU/内存。Fuzz 覆盖随机字节、极深结构、超大字段、非法 UTF-8/Surrogate 和 Logical ID。

### 高频面试题

#### Q：为什么 Draft Save 不能直接复用 Publish Validator？

Web 自动保存时画布经常暂时断边、缺节点或字段未填完。Parser 只保证输入是有界、无歧义、字段属于 IR 的安全文档；Publish Validator 则保证引用、类型、节点契约以及后续 Control Graph 全部可执行。放宽保存不能等价于放宽执行。

#### Q：JSON Schema 已经存在，为什么还要 Go Validator？

Schema适合跨语言约束单个 JSON 文档的形状，但不能完整表达跨 Node Output 的 Ref 存在性、名称唯一、Catalog Revision 语义和面向 Agent 的稳定错误位置。两者是外部形状契约与领域语义校验的分工，不是重复实现。

#### Q：为什么 Canonical JSON 不能直接 `json.Marshal(map)`？

Hash 要跨进程和版本稳定，需要明确 Object Key、Array、String、Number 与重复 Key 规则。尤其 Number 不能先转 `float64`，否则大整数和十进制值可能改变。Canonical 规则必须由 Golden Fixture 固定，而不是依赖“当前库碰巧输出一致”。

#### Q：为什么 Catalog Revision 不放进 IR？

IR 是作者意图，Catalog Revision 是平台解释该意图时使用的内部契约坐标。Draft 外层固定 Catalog，Published Snapshot 固定编译产物；Web/Agent 只提交无版本号 Node Type，从而不会被内部版本升级污染。

### 一分钟讲法

M1 把 Human Web 和 Agent CLI 的共同作者语言做成了真正的 Contract。IR 采用统一浅层 Node 外壳，Web UUID 与 Agent 语义 ID 同时受稳定词法规则约束；六种 JSON 顶层类型只有 integer 到 number 的提升。Draft Parser 允许安全半成品保存，Strict Validator 必须绑定内部版本化 Catalog，公开 Description 不暴露 Node Version。Canonical JSON 使用精确十进制、Object 排序和 Array 保序生成 SHA-256 Hash，并用版本化正反例、100 次重复、Fuzz 和 Race Test 固定行为。

### 五分钟展开提示

1. 先解释 IR 是作者态权威、DSL 是运行态产物；
2. 展开统一 Node/Input/Output/Edge/Layout 与离线 Logical ID；
3. 对比 Draft Parser 和 Strict Validator 的失败边界；
4. 说明 JSON Schema 与领域 Validator 为什么缺一不可；
5. 解释 Catalog Revision 内部化和新增 Node 的注册路径；
6. 展开 Decimal、Canonical JSON、Hash 与重复 Key/Unicode 安全；
7. 最后给出 Fixture、Contract、100 次重复、Fuzz 和 Race 证据链。

### 易错点与追问

- M1 的 Strict Validator 单独使用时不包含 DAG、Branch Route 完整性和 `Active(Target) ⇒ Active(Source)`；Test/Publish 必须继续组合 M2 Compiler Pipeline；
- M1 有 IR Contract，不等于已经存在 Draft API、数据库版本模型或 CLI 上传命令；
- Catalog 是进程内版本化契约，不是独立 Registry 微服务；
- `number` 是精确 JSON Decimal 语义，不是 `float32/float64`；
- Object 内部允许 Null，但六种顶层类型不包含 Null；
- Layout 参与 IR Hash，但未来 Compiler 必须忽略 Layout，因此布局变化不应改变 DSL Hash。

## 7. M2：Compiler、DSL、Source Map 与 Control Graph

- 验收状态：已通过 Unit、JSON Schema Contract、Golden、100 次确定性、20 次 Contract Repeatability、Vet、Build、Linux Race 与集成测试；远端 CI 由本模块分支提交触发。
- 学习价值判断：写入。
- 判断理由：IR/DSL 职责、Execution ID、Source Map、Control Graph 激活语义和 Compiler SPI 都属于一旦错误便会污染所有历史发布版本的底层边界，也是面试中编译器、DAG 静态分析、插件化和确定性构建的高价值主题。

### 解决的问题

M2 把 M1 的作者意图转换为 Runtime 可独立执行的不可变契约。Runtime 不需要读取 Draft、IR、Layout 或 Node Description；结构性错误、Branch Route 错误和不安全数据引用在 Test/Publish 阶段失败，不能拖到 Worker 执行后才暴露。

### 核心边界与不变量

- Compiler 是纯 Domain Module，不导入 HTTP、PostgreSQL、Redis、Kafka 或任何 Adapter；
- DSL 与 IR 使用独立 Go Model，DSL 只保存 Execution ID、Operation、Binding、Output Contract 和最终 Execution Policy；
- 第一阶段保持一个 IR Node 对应一个 DSL Node，但 ID 命名空间仍分离；
- Control Edge 只编译为 `always` 或 `route` Activation，数据引用编译为 `node_output` Binding；
- Start/End/Branch 是 Control Operation，不创建 Attempt；Code/HTTP/RPC 是 Task Operation；
- Runtime 开始任何 Node 前扫描完整 DSL 的 Operation Version，不能执行一半才发现 Handler 不兼容；
- Source Map 覆盖每个 Execution Node、Edge 和可报告 Field；精确 Field 缺失时只回退到 Node，不猜测位置；
- 相同 IR、Catalog、Policy 和 Resource Bindings 必须产生字节级相同的 DSL、Source Map、Manifest 和 Hash。

### 编译流水线

```text
Strict IR + Catalog Validation
→ Control Graph Validation
→ Active/Reference Safety Analysis
→ Deterministic Execution ID
→ Policy + Resource Binding Resolution
→ Handler Registry 编译 Operation
→ DSL Self Validation
→ Full Operation Compatibility Check
→ Source Map Coverage Validation
→ Canonical JSON + Hash
```

任何阶段出现 Error Diagnostic 都停止产生执行产物。Compiler 不返回“部分可运行 DSL”，因为部分产物一旦被错误持久化，就会破坏 Published Version 的不可变性和可恢复性。

### DSL v1 为什么不是 IR 的复制

Code 的 `source_code` 从 IR Input 进入 `operation.config`，普通数据进入 Runtime `inputs`；HTTP 的 `connection_ref` 被授权后的稳定 `connection_id` 替代；RPC 固化 `service_id/contract_revision/idempotent`；Edge Route 变成强类型 Activation。IR 的 Title 与 Layout 完全不进入 DSL。

Literal Binding 保存 Canonical JSON；Ref Binding 使用：

```json
{
  "kind": "node_output",
  "data_type": "object",
  "output": {
    "node_id": "xn_...",
    "name": "payload"
  }
}
```

这使 Engine 只按 Execution Snapshot 工作，也让未来 IR 编辑体验演进时不必改写历史 Runtime 语义。

### `Active(Target) ⇒ Active(Source)` 如何实现

仅检查 Source 能到达 Target 不够。排他分支汇合后，Target 可能通过另一条 Route 激活，而 Source 所在 Route 未激活。M2 先用 DAG 位集合闭包检查 Source 确实是控制上游，再使用有序多值决策图 MDD 表达每个 Node 的激活条件：

```text
Start = true
普通 Edge = Active(Source)
Branch Edge = Active(Branch) AND SelectedRoute == Edge.Route
多入边 Node = OR(所有入边条件)
```

最后判断 `Active(Target) AND NOT Active(Source)` 是否存在可满足赋值。MDD 的 Unique Table 与 Apply Memo 共享等价子图，不枚举 Route 笛卡尔积；超过安全复杂度上限时失败关闭，不能近似放行。

经典 Dominator 不够，因为普通 Node 多出边会并行激活：并行节点可能始终一起运行，但彼此不在所有路径上。单纯穷举 Route 又会随独立 Branch 数量指数增长。

### Source Map 与错误定位

Source Map 是三个直接索引：

```text
nodes[execution_node_id] → logical_node_id
edges[execution_edge_id] → logical_edge_id
fields[execution_node_id][dsl_field] → ir_field
```

例如 Worker 报告 `operation.config.source_code`，Control Plane 可定位为 `inputs.source_code`；Worker 只报告 Execution Coordinate，不携带 Source Map 或 IR。字段不存在映射时保留 Node 定位，这比编造错误字段更可靠。

### 确定性 ID、Manifest 与 Hash

Execution ID 使用带 DSL Version 和对象类别命名空间的 SHA-256 截断值，分别加 `xn_`/`xe_` 前缀。它不依赖数据库发号、Node 数组下标或部署拓扑，并执行碰撞检测。

```text
ir_hash         = Hash(Canonical Full IR，包含 Layout)
dsl_hash        = Hash(Canonical DSL)
source_map_hash = Hash(Canonical Source Map)
definition_hash = Hash(三个 Hash + Compiler Manifest)
```

Manifest 固定 `compiler_version/catalog_revision/policy_revision`。只改 Layout 时，IR/Definition Hash 改变，但 DSL/Source Map Hash 不变；只改 Policy Revision 且最终 Policy 内容不变时，只有 Definition Hash 变化。这能区分“作者内容变化”“运行语义变化”和“编译解释坐标变化”。

### Compiler Handler SPI 与节点扩展

Compiler 使用 `node_type → Handler` Registry。Handler 声明 Node Type、Control/Task Kind、Operation Coordinate，并编译 Operation Config 与 Runtime Binding。Catalog 另行保存内部 Runtime Contract，Compiler 会检查两者一致。新增普通 Task Node 的路径是：

```text
Catalog Contract + Compiler Handler + DSL Operation Contract + Executor + Routing Policy
```

不修改 IR Validator 的中心 `switch-case`，也不修改 Engine 或 Scheduler。Start/End/Branch 属于 Control 语义，新增 Control Node 仍需要受控升级 Compiler 与 Engine。

### Managed Resource 与 Policy 输入

M2 不访问资源数据库。M3 将负责 Principal/Project 授权并把 `connection_ref/service_ref/model_ref` 解析为只含稳定 ID、Contract Revision、Digest 和幂等能力的 Resource Bindings。Compiler 只消费这个不可变值对象，因此既能固化 DSL，又不让 Secret、Endpoint 或外部 I/O 破坏确定性。

Execution Policy 来自 Catalog Default 与 Project Policy，不来自作者 IR。DSL v1 固化 Attempts、Recoveries、Attempt Timeout、固定 Backoff 和 Retryable Error Codes。默认采用保守单次业务 Attempt；Code 不允许业务自动重试，非幂等 HTTP/RPC 也不能被策略强行配置为多次业务 Attempt。

### 数据库、Redis 与 Kafka 在 M2 的角色

三者在 M2 都没有运行时角色：

- PostgreSQL 将在 M3 保存 IR/DSL/Source Map/Manifest/Hash 的不可变 Execution Snapshot；M2 只产生值对象；
- Redis 不能参与编译或 Hash，否则缓存命中、TTL 或实例切换可能改变发布产物；
- Kafka 不发送 Definition Event，也不承载 Compiler Pipeline；没有消费者的发布事件只会增加一致性负担。

这是“技术栈服务领域边界”的例子：简历可以展示 PostgreSQL、Redis、Kafka，但不能把它们硬塞进应当纯函数化的 Compiler。

### 一致性、安全与水平扩展

Compiler 无状态且输出确定，同一请求可以在任意 Control Plane 实例重复执行并得到相同 Hash，因此天然支持水平扩展。真正的 Publish 幂等与 Snapshot 事务在 M3 完成；M2 不通过 Redis 锁或 Kafka 顺序制造伪一致性。

安全方面，作者 Resource Ref 必须先变成已授权稳定绑定，Secret 没有进入 DSL 类型的表达方式；Runtime DSL 会重新检查容器、Binding、Operation Config、图结构和全部 Operation Version。Source Map 缺失、Compiler/Catalog 坐标不一致、ID 碰撞和分析复杂度超限都失败关闭。

### 高频面试题

#### Q：既然第一阶段 Node 一对一，为什么还要 DSL？

一对一只描述节点数量，不代表字段语义相同。Compiler 需要固化 Operation Version、资源 ID、执行策略、强类型 Binding 和 Edge Activation，并移除 Layout/Title。Runtime 直接执行 IR 会同时耦合作者体验、Catalog 当前版本和基础设施解析，历史发布版本无法稳定复现。

#### Q：为什么 Source Map 不直接塞进 Kafka Task？

Worker 只需执行当前 Attempt 并报告 Execution Coordinate。Source Map 属于 Definition Snapshot，放进每个 Task 会放大消息、泄漏作者结构并产生多份一致性副本。Control Plane 在错误返回 Web/CLI 前统一增强即可。

#### Q：为什么不能只检查 DAG 和 Ref Source 可达？

可达只证明存在一条 Source 到 Target 的路径，不证明 Target 每次激活时 Source 都激活。排他分支的另一条 Route 可以绕过 Source，因此还必须证明激活蕴含关系。

#### Q：Compiler 为什么不查数据库或 Redis？

外部 I/O 会让相同输入受瞬时状态影响，破坏可重复构建。应用层先把授权后的 Catalog、Policy、Resource Bindings 固化为输入值，Compiler 再纯函数化生成产物；数据库事务负责保存，不参与语义计算。

#### Q：Operation Version 和 Executor Build Version 有何区别？

Operation Version 是不可变运行语义坐标，不兼容变化必须升级；Executor Build Version 是实现构建，用于审计和修复，同一 Operation Version 下不能改变可观察语义。Runtime 必须先检查 Operation Version，不能依赖“最新 Worker 大概兼容”。

### 一分钟讲法

M2 把作者态 IR 编译为 Runtime 独立的 DSL v1，同时生成 Source Map、Compiler Manifest 和四类 Hash。Compiler 是无基础设施依赖的确定性 Domain Module；Task Node 通过 Handler Registry 扩展，不靠中心 Switch。Control Graph 在发布前检查单入口单出口 DAG、Branch Route、OR-Join 和数据引用激活蕴含，后者用多值决策图精确分析。Runtime 在执行前自校验完整 DSL 和 Operation Version，Worker 错误再通过 Source Map 精确回到 IR 字段。100 次重复编译、Golden、Schema、Source Map 覆盖和架构依赖测试共同固定了这条边界。

### 五分钟展开提示

1. 从 Human/Agent 共用 IR、Runtime 只读 DSL 讲职责分离；
2. 展开 Operation Config、Runtime Binding、Edge Activation 与 Execution Policy；
3. 用排他分支反例解释为什么可达不等于安全；
4. 说明 MDD 相对 Dominator 和枚举的优势；
5. 展开 Execution ID、Source Map 精确定位与 Node 回退；
6. 解释 Manifest 和四类 Hash 如何支持不可变 Snapshot；
7. 说明 Handler SPI 与普通 Task Node 扩展路径；
8. 最后强调 PostgreSQL/Redis/Kafka 为何此阶段都不进入 Compiler，以及测试证据链。

### 易错点与追问

- M2 产生 Execution Snapshot 的内容值，但 M3 才负责数据库中的 Draft/Published Version 与 Snapshot 事务；
- Resource Bindings 是未来 Resources 模块的输入 Port，不代表当前已创建 Connection/Service 数据库；
- Branch Runtime 求值、Node Run/Attempt 状态机属于 M4，不要把静态编译等同于已经可以运行 Workflow；
- Code Python 完整语法/Import 检查与强隔离执行仍需 M9 Sandbox 完成；
- Source Map 不进入 DSL 或 Kafka，DSL 也不携带 Logical ID；
- MDD 超限必须拒绝发布，不能为了“尽量运行”退化成不安全近似；
- 当前固定 Backoff 是 DSL v1 语义，未来新增 Backoff 形态必须保持旧 Operation/DSL 兼容。
