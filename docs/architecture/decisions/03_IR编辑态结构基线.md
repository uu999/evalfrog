# IR 编辑态结构基线

> 状态：Accepted Baseline
>
> 日期：2026-08-07
>
> 范围：Human Web 与 Agent CLI 共用的 IR 结构、标识、引用、布局和版本隔离
>
> 前置基线：[00_核心架构决策基线.md](./00_核心架构决策基线.md)、[02_节点模型与执行能力边界.md](./02_节点模型与执行能力边界.md)

## 1. IR 的职责

IR 是 Workflow Draft 的编辑态权威来源，也是 Published Version 中用于 Copy、Diff、审计和错误回溯的不可变源快照。

同一份 IR 同时服务两种作者：

```text
Human Web 画布 ─┐
                ├─ 读取和写入同一种 canonical JSON IR
Agent CLI/API  ─┘
```

IR 必须适合局部阅读和增量修改，但不承担 Runtime 的执行约束。Runtime 只执行 Compiler 生成的 DSL。

## 2. 顶层结构

第一阶段 IR 使用 `application/json`，核心结构保持浅层：

```json
{
  "ir_version": "1",
  "nodes": [],
  "edges": [],
  "layout": {}
}
```

- `nodes`：节点及其输入、输出声明；
- `edges`：控制流关系；
- `layout`：共享画布布局；
- 不设置独立的 `bindings` 集合，数据引用直接表达在 Node Input 中；
- Workflow 名称、描述、所有者等领域元数据由 Workflow/Draft 外层记录持有，不为运行图重复造一份权威数据。

## 3. Node 的统一表达

所有 Node Type 使用相同的公共外壳：

```json
{
  "id": "build_order",
  "type": "code",
  "title": "构造订单",
  "inputs": [],
  "outputs": []
}
```

冻结规则：

1. `id` 是该 Workflow 定义内的逻辑节点身份，必须唯一且跨 Revision 尽量稳定。
2. `type` 是不带版本号的业务类型，例如 `start`、`code` 或 `http`。
3. `title` 只面向 Human 和 Agent，修改标题不得改变 `id`。
4. 不设置 `params` 或 `config` 分区；节点需要的值统一进入 `inputs`。
5. 节点契约版本不进入 IR，Agent 和 Web 不选择也不提交内部版本号。
6. 不同 Node Type 的语义差异由 Node Description 约束，不改变公共 JSON 外壳。

## 4. Input

`inputs` 是列表。每项都是一个具有统一结构的 JSON 对象：

### 4.1 Literal Input

```json
{
  "name": "method",
  "data_type": "string",
  "source": "literal",
  "value": "POST"
}
```

### 4.2 Reference Input

```json
{
  "name": "body",
  "data_type": "object",
  "source": "ref",
  "ref_node": "build_order",
  "ref_output": "result"
}
```

Input 不变量：

- 同一 Node 内 `name` 唯一；
- `source` 只能是 `literal` 或 `ref`；
- `literal` 必须包含 `value`，不得包含 `ref_node`、`ref_output`；
- `ref` 必须包含 `ref_node`、`ref_output`，不得包含 `value`；
- `ref_node` 必须存在，`ref_output` 必须是该 Node 声明的输出；
- 引用源必须在控制图上能够到达当前 Node；
- 进一步要求：只要当前 Node 可能被激活，其必需引用源就必须处于同一条必然激活路径，不能把不安全引用延迟到 Runtime 才发现。

节点配置和运行数据不再使用两套绑定机制。例如 HTTP 的 `connection_ref`、`method`、`relative_path` 是 Literal Input，而请求 `body` 可以是 Literal Input 或 Reference Input。

## 5. Output

`outputs` 是节点结果契约的平面列表：

```json
[
  { "name": "result", "data_type": "object" }
]
```

同一 Node 内 Output `name` 必须唯一。IR 只声明输出名称和数据类型，不包含任何 Runtime 输出值。

### 5.1 第一阶段类型系统

`data_type` 第一阶段只允许六种顶层 JSON 类型：

```text
string
integer
number
boolean
object
array
```

类型不变量：

- 不提供 `any`，避免静态引用校验失去意义；
- 不允许顶层 `null`，但 `object` 和 `array` 内部可以包含 JSON `null`；
- `integer` 使用 JavaScript 安全整数范围 `[-9007199254740991, 9007199254740991]`，更大整数和数字型标识使用 `string`；
- `number` 表示 JSON 十进制数，比较时使用十进制 Decimal 语义，不直接使用 `float32/float64` 的二进制浮点比较；
- IR 不内嵌完整 JSON Schema，第一阶段只校验顶层类型；
- Literal 的真实 JSON 值必须符合其声明的 `data_type`；
- Ref 只能引用一个完整的命名 Output，不支持通过 `response.user.name` 一类路径截取内部字段；
- 除 `integer` 可以安全赋给 `number` 外，其他 Input/Output 类型必须完全相同；
- 不进行字符串、数字或布尔值之间的隐式转换。

Compiler 在 Draft Test 和 Publish 时检查 Ref Output 与目标 Input 的类型兼容性。Worker 返回结果后，Runtime 还必须校验真实 Output 的顶层类型；不匹配时 Node Run 失败并产生结构化错误：

```text
error_code = OUTPUT_TYPE_MISMATCH
ir_node_id = {node_id}
ir_field = outputs.{output_name}
expected
actual
```

## 6. Edge

Edge 只表达控制流，不承担数据传递：

```json
{
  "id": "build_order_to_create_order",
  "source": "build_order",
  "target": "create_order"
}
```

Branch 的出边额外使用 `route`：

```json
{
  "id": "check_order_to_manual_review",
  "source": "check_order",
  "target": "manual_review",
  "route": "needs_review"
}
```

Edge 不变量：

- `id` 在 Workflow 定义内唯一，并作为 Edge 的逻辑身份；
- `source` 和 `target` 都引用 Node ID；
- 不设置 `source_port` 或 `target_port`；
- `route` 只允许出现在 Branch 的出边；
- Edge ID 由作者离线生成。Agent 应优先使用 `node1_to_node2` 一类语义 ID，Web 可以生成随机稳定 ID。

## 7. Layout

`layout` 是共享编辑语义的一部分。例如：

```json
{
  "start": { "x": 80, "y": 160 },
  "build_order": { "x": 320, "y": 160 },
  "create_order": { "x": 560, "y": 160 },
  "end": { "x": 800, "y": 160 }
}
```

- Web 画布直接读取 IR 的 Layout；
- Agent 可以生成质量较差但结构有效的布局；
- 修改 Node 坐标属于 IR 变化，并产生新的 `draft_revision`；
- Compiler 完全忽略 Layout，因此只修改布局时，生成的 DSL 可以保持不变；
- 缩放比例、滚动位置、当前选中节点等个人会话状态不进入 IR。

## 8. ID 生成与 Source Map

IR Node ID 和 Edge ID 都由作者离线生成，不依赖服务端发号：

- Web 使用随机且稳定的 ID；
- Agent 使用便于理解和修改的语义 ID；
- 服务端负责作用域内唯一性和格式校验。

DSL 的 Execution Node/Edge ID 由 Compiler 在编译过程中生成，同样不依赖数据库发号。第一阶段保持一个 IR Node 编译为一个 DSL Execution Node，但 IR ID 与 DSL ID 仍是不同命名空间。

Source Map 使用便于直接索引的 Key-Value 结构：

```json
{
  "source_map_version": "1",
  "nodes": {
    "xn_calculate_order_92ab": "calculate_order"
  },
  "edges": {
    "xe_calculate_to_create_701a": "calculate_order_to_create_order"
  },
  "fields": {
    "xn_calculate_order_92ab": {
      "operation.config.source_code": "inputs.source_code",
      "inputs.amount": "inputs.amount",
      "outputs.total": "outputs.total"
    }
  }
}
```

`nodes` 和 `edges` 分别提供 Execution ID 到 IR ID 的直接查询。`fields` 先按 Execution Node ID 定位，再将 DSL Relative Field 映射为 IR Relative Field。Field 只负责 Node 内部定位，不承担 Node 查找：

```text
inputs.{input_name}
outputs.{output_name}
inputs.cases.{route}.{field}
```

Runtime Error 没有具体字段时可以只携带 Execution Node ID；不存在精确 Field Mapping 时回退到整个 IR Node。Source Map 不进入 Kafka Task，Worker 只报告 Execution ID、可选 `dsl_field` 及源码行列，Control Plane 负责映射。Publish 前必须验证所有 Execution Node/Edge 都有来源；映射缺失属于编译产物完整性错误。第一阶段不引入 Binding ID。

## 9. Node Description 与内部版本

Web 和 Agent 通过 Node Description 理解可用节点：

```text
type
自然语言能力描述
允许的 inputs：名称、允许类型、必填性、允许的 source、枚举或范围约束
outputs：固定声明，或允许作者声明的名称和类型范围
示例
```

Node Description 不暴露节点契约版本。Agent 的职责是根据用户意图和当前描述选择 `type`，并填充统一的 `inputs`、`outputs`。

平台内部维护版本化 Node Catalog，并遵守：

1. Draft 外层记录内部 `catalog_revision`，不把它写入作者 IR。
2. 已存在 Draft 不因 Catalog 更新而静默改变语义。
3. 契约变化时返回 `NODE_DEFINITION_CHANGED`，显式迁移后形成新的 Draft Revision。
4. 新建节点默认使用当前 Node Description。
5. Published Version 冻结 IR、DSL、Source Map、Compiler Manifest 与内部 Runtime Operation 版本，不随 Catalog 更新。
6. Copy Published Version 使用其中保存的 IR 创建新 Draft，再按当前 Catalog 校验或显式迁移；不需要从 DSL 反编译 IR。

### 9.1 Retry 与 Timeout 的定义边界

第一阶段不允许作者在 IR 中覆盖 Retry 或 Timeout，也不把它们伪装成 Node Input。Compiler 在 Draft Test 或 Publish 时，根据内部 Node Catalog 默认值和 Project Policy 解析最终执行策略，并将结果固化进不可变 DSL。

未来如需作者覆盖，必须为所有 Task Node 增加统一的可选 `execution_policy`，不能由不同 Node Type 分别发明配置字段；该扩展不属于第一阶段 IR。

## 11. IR 与 DSL 的边界

IR 采用统一、浅层、作者友好的表达；DSL 可以为 Runtime 深度嵌套，并完成：

- 类型和必填项归一化；
- 默认值固化；
- Reference 解析；
- Connection/Service 等受管资源引用解析；
- Control Graph 与 Runtime Operation 编译；
- 内部 Operation 版本和执行策略固定；
- Source Map 生成。

因此即使第一阶段是一对一 Node 编译，也不能让 Runtime 直接执行 IR，更不能把 DSL 当作长期编辑源。

DSL 只能由服务端 Compiler 生成，并满足：

- 自包含执行语义，Runtime 不再读取 IR 或 Node Description；
- Test Run 与 Published Version 引用的 Execution Snapshot 中，DSL 均不可变；
- 不包含 Layout、Title、Kafka Topic、Worker 地址等编辑态或基础设施信息；
- 使用由 Compiler 离线、确定性生成的独立 Execution Node/Edge ID；
- 不携带 IR Node/Edge ID 或 IR Path，所有来源关系由独立 Source Map 保存。

第一阶段 DSL 顶层最小结构为：

```json
{
  "dsl_version": "1",
  "entry_node_id": "xn_start_7f2a",
  "exit_node_id": "xn_end_93bc",
  "nodes": [],
  "edges": []
}
```

Execution Node 使用统一外壳：

```json
{
  "id": "xn_create_order_a81c",
  "kind": "task",
  "operation": {
    "type": "http",
    "version": 1,
    "config": {}
  },
  "inputs": {},
  "outputs": {},
  "execution_policy": {}
}
```

- `kind` 只能是 `control` 或 `task`；
- `operation.type/version` 是 Runtime Handler 的内部坐标；
- `operation.config` 保存已经归一化的节点专用配置；
- `inputs` 保存 Literal 或上游 Execution Output Binding；
- `outputs` 保存 Runtime 输出契约；
- `execution_policy` 保存 Compiler 已解析的 Retry、Timeout 等最终值。

Compiler 可以重新组织 IR。例如 Code 的 `source_code` 从 IR Input 编译到 `operation.config`，数据 Ref 则转换为使用 Execution Node ID 的 Runtime Input Binding。Control Edge 也从 IR 的可选 `route` 归一化为 `activation.kind=always|route`。因此 DSL 不是 IR 的字段复制品。

### 11.1 Compiler 流水线

```text
读取确定 Draft Revision
→ 解析 IR Version
→ Node Contract 校验
→ Control Graph 校验
→ Ref/Type/Active 安全校验
→ 受管资源与权限解析
→ 默认执行策略解析
→ 确定性生成 Execution ID
→ 编译 Operation、DSL 与 Source Map
→ DSL 自校验
→ Canonicalize 与 Hash
```

Draft Save 允许不完整；Draft Test 与 Publish 使用同一 Compiler。第一阶段不做 Node 融合、删除或重排，保持一对一编译。相同语义 IR、Compiler、Catalog 和 Policy 必须生成相同 DSL。Validation 返回数量有上限、顺序稳定的结构化错误列表，至少包含 `phase/error_code/ir_node_id/ir_edge_id/ir_field/message`。

### 11.2 Operation 编译坐标

| IR Node | DSL Operation | Operation Config | Runtime Input |
|---|---|---|---|
| Start | `control.start@1` | 空 | Run Input |
| End | `control.end@1` | 空 | `workflow_output` |
| Branch | `control.branch@1` | Cases、Default Route | `value` |
| Code | `task.python@1` | Source Code、固定沙箱契约、Model Artifact | 命名数据 Input |
| HTTP | `task.http@1` | Connection ID、Method、Accepted Statuses | Path、Query、Headers、Body |
| RPC | `task.rpc@1` | Service ID、Operation、Contract Revision、幂等能力 | Request |

内部 Node Catalog 标记每个 IR Input 应编译为 Operation Config 还是 Runtime Data Input；该差异不改变作者看到的统一 IR Input 结构。

### 11.3 受管资源与兼容性

- `connection_ref` 编译为稳定 `connection_id`，Credential 和当前网络配置在 Runtime 解析；
- `service_ref + operation` 编译为稳定 Service ID 与内部 Contract Revision，Endpoint 和认证在 Runtime 解析；
- `model_ref` 编译为不可变 Model Artifact ID/Digest；
- Secret 明文永远不进入 DSL；Attempt 记录实际使用的受管资源 Revision；
- Runtime 不再读取 IR 或 Node Catalog，但仍可访问 Connection、Service Discovery 和身份服务。

`dsl_version`、`operation.version`、`executor_build_version` 分别表示 DSL 结构、Operation 语义和执行器构建。Runtime 必须在开始执行任何 Node 前检查全部 Operation Version；不支持时返回 `RUNTIME_OPERATION_UNSUPPORTED`。旧 Handler 的既有语义不得被覆盖，只要仍有 Published Version 或保留期内 Run 引用就不能删除。

### 11.4 完整性 Hash

```text
ir_hash         = Hash(Canonical Full IR，包含 Layout)
dsl_hash        = Hash(Canonical DSL)
source_map_hash = Hash(Canonical Source Map)
definition_hash = Hash(ir_hash + dsl_hash + source_map_hash + compiler_manifest)
```

Compiler Manifest 至少包含 `compiler_version/catalog_revision/policy_revision`。创建时间和创建人不参与 Hash。只修改 Layout 时，`ir_hash` 与 `definition_hash` 改变，`dsl_hash` 与 `source_map_hash` 不变。
